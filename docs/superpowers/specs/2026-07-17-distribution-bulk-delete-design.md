# 内容分发中心批量删除设计

## 目标

在“自动发布”和“Telegram 广播”两个页面增加批量选择与批量删除，方便运营人员一次清理多条任务，同时避免误删、重复提交和部分失败后状态不清晰。

本次只增加批量删除，不扩展批量启停、批量编辑或跨页面选择。现有单条编辑、启停、验证、测试和删除能力保持不变。

## 交互设计

- 自动发布规则和 Telegram 广播规则分别维护自己的选中状态，互不影响。
- 每条规则左侧增加复选框；规则列表顶部增加“全选当前列表”“清空选择”和“删除选中（N）”。
- “全选当前列表”只选择当前页面已经加载并显示的规则，不选择其他入口或不可见数据。
- 未选中规则时，“清空选择”和“删除选中”不可用。
- 点击“删除选中（N）”后必须二次确认，确认文案明确展示删除数量和当前规则类型。
- 删除执行期间禁用批量按钮和相关单条删除按钮，防止重复提交。
- 删除完成后自动刷新列表和数量；成功删除的规则从选择中移除，失败的规则保留选中，便于再次处理。
- 页面刷新或重新进入后不保留选择状态，避免把临时操作状态误认为持久配置。
- 单条删除入口继续保留，降低只删除一条规则时的操作成本。

## 状态与数据流

页面分别保存 `selectedAutomationIds` 与 `selectedBroadcastIds`，只存规则 ID。每次规则列表刷新后，将选中集合与当前列表取交集，自动清理已经不存在的 ID。

批量删除使用一次管理接口请求提交去重后的规则 ID。服务端逐条执行现有删除语义，返回每个 ID 的处理结果；前端根据结果显示成功数、失败数及失败原因，并只保留失败项的选中状态。

## 接口约定

请求：

```json
{
  "action": "delete-many",
  "ids": ["rule-a", "rule-b"]
}
```

成功响应：

```json
{
  "ok": false,
  "requested": 2,
  "deleted": 1,
  "failed": 1,
  "results": [
    { "id": "rule-a", "ok": true },
    { "id": "rule-b", "ok": false, "error": "规则不存在或已删除" }
  ]
}
```

规则：

- `ids` 必须是非空字符串数组，服务端先去重并拒绝空请求。
- 单次最多删除 100 条，超过限制返回明确的参数错误。
- 单项不存在或删除异常不影响其他规则继续处理，响应必须给出逐项明细。
- 只有全部条目成功时顶层 `ok` 才为 `true`；部分成功时仍返回可解析的结果明细，前端不得把它显示成“全部成功”。
- 接口继续沿用后台登录鉴权，不向公开 Webhook 暴露。

## 错误与可访问性

- 请求整体失败时保留全部选择，并显示服务端错误，允许用户重试。
- 部分失败时提示“已删除 X 条，Y 条失败”，失败项保持勾选。
- 复选框有包含规则名称的可访问标签；全选复选框支持未选、部分选中和全选三种视觉状态。
- 批量操作栏在 1366×768 和窄屏下都不遮挡规则内容，按钮可通过键盘操作，并提供清晰的加载状态。

## 测试与发布门禁

- 单元测试覆盖空数组、重复 ID、超过 100 条、全部成功、部分失败和全部失败。
- 前端测试覆盖单选、全选、清空、二次确认、提交期间禁用、成功后清空和部分失败保留。
- 回归现有单条删除、启停、验证、测试消息、自动任务和 Telegram 广播配置保存。
- 全量自动化测试通过后部署生产，在自动发布与 Telegram 广播各创建可删除测试规则，验证批量删除、页面刷新和其他设备重新登录后的结果一致。
